# Absorb — Pipeline & Agent Reference

*This document explains the `absorb` plugin itself: every MCP tool it exposes, every agent it can spawn, every skill each agent reads, how they're wired together, and where each piece lives on disk. It was generated by direct inspection of this repository on 2026-08-13 — every path, tool name, and quoted instruction below is copied verbatim from the actual files, not paraphrased. Where something in the repo looks like a bug or dead code, it's called out explicitly rather than silently worked around, per this project's own grounding standard (see `docs/absorb-review-findings.md` for the fuller review this triggered).*

## 1. What this plugin is

`absorb` (`plugin.json`, version `2.0.0`) is a Gemini CLI plugin: one MCP server (`server.py`) plus a fleet of Gemini CLI sub-agents and skills that together generate three audience-specific documentation sets for a target codebase — **User**, **Developer**, and **Agent** — using what the plugin calls the "Chunked Writer Architecture." A separate, self-contained sub-system (the **Commit Analyzer**) generates git-history "Delta Reports" between two commits.

Two entirely different pipelines live in this one plugin:
1. **The Absorb documentation pipeline** — orchestrated by the `absorb` skill, running three parallel per-audience tracks (User / Developer / Agent), each a 10-stage chunked-writer pipeline with its own agent fleet.
2. **The Commit Analyzer** — orchestrated by the `commit-analyzer` skill, a smaller 3-role fan-out/fan-in pipeline (Orchestrator → N Writers → 1 Compiler) for git delta reports.

## 2. The MCP server (`server.py`)

```python
mcp = FastMCP("Absorb Documentation Server")
DOCS_DIR = r"d:\working docs\absorb_docs"
```

| Type | Name | Signature | What it actually does |
|---|---|---|---|
| Tool | `trigger_absorb_pipeline` | `(target: str = "all", repo_path: str = "d:\CreatorOS") -> str` | Does **not** run the pipeline itself. Returns the literal string: `"Instruction for Agent: Please invoke the /absorb slash command on {repo_path} with target={target}."` — i.e. it's a redirect telling the calling agent which slash command to invoke next. `target` accepts `'user'`, `'developer'`, `'agent'`, or `'all'`. |
| Tool | `analyze_commit_delta` | `(commit_start: str, commit_end: str, repo_path: str) -> str` | Same pattern — returns an instruction string telling the agent to invoke the `commit_analyzer_agent` subagent with the given repo path and commit range, and to follow the `commit-analyzer` skill. |
| Resource | `get_module_docs` | `absorb://docs/{target}/{module}` | Reads `{DOCS_DIR}/{target}/{module}.md` from disk and returns its contents, or a "not found or pipeline hasn't run yet" message if the file doesn't exist. This is the *read* side — it serves docs the pipeline already generated; it does not generate anything itself. |

`mcp_config.json` registers this server as `absorb`, launched via `python server.py`.

**Note on `DOCS_DIR`:** the server reads from `d:\working docs\absorb_docs` (correctly formed, single backslash pairs). This does **not** match the output path written in the orchestrator skill's own instructions — see §6, "Known issues."

## 3. The Absorb documentation pipeline

### 3.1 Orchestrator

**Skill:** `skills/absorb/SKILL.md` — invoked as the `/absorb` slash command. No dedicated orchestrator *agent* file exists for this skill; it runs as instructions for whichever agent context invokes `/absorb` (i.e. the top-level Gemini CLI session itself acts as orchestrator).

The skill's own text, stage by stage (quoted, condensed):

| Stage | Name | Instruction (as written) |
|---|---|---|
| — | Initialize | Determine the target (`user`, `developer`, `agent`, or `all`) and `<base_repo_path>`. |
| 0 | Architect | Trigger the Architect Agent to traverse the codebase and determine the optimal number of chunks (N) and their distinct scopes based on complexity. |
| 1 | Discovery | Trigger specific Discovery Agents for the active tracks to map the repo. |
| 2 | Analysis | Trigger Analysis Agents to extract deep facts. |
| 3 | Synthesis | Trigger Synthesis Agents to generate a strict, modular outline corresponding to the Architect's N chunks. |
| 4/5 | Chunked Drafting | **Critical step.** Invoke exactly N parallel Writer Agents (e.g. `user_writer_agent`). Assign ONE specific chunk/module to EACH agent to ensure exhaustive detail. |
| 5.5 | Critic Loop | For each drafted chunk, invoke the Critic Agent. If it outputs required revisions, re-invoke the Writer Agent for that chunk with the feedback, producing a V2. Repeat until the Critic outputs `APPROVED`. |
| 6 | Compilation | Once all N chunks are approved, invoke the Compiler Agent to stitch them into a single document using the Rolling Editor technique. |
| 7 | Review | Pass the master document to the Review Agent for consistency. |
| 8 | Grounding | Pass the reviewed document to the Grounding Agent for final verification. |
| 9 | Exporter | Invoke the Exporter Agent to convert the final Markdown into a styled PDF. |
| — | Final Output | Save the final `.md` and `.pdf` to `d:\working docsbsorb_docs\<target>\` *(literal text in the file — see §6, this path is malformed)*. |

**This is the authoritative wiring:** the orchestrator explicitly names `user_writer_agent` as its example Writer Agent — i.e. the live pipeline invokes the **track-prefixed** agent families (`user_*`, `dev_*`, `agent_*`), not the generic `absorb_*` family described in §4 below.

### 3.2 The three tracks

Three isolated pipelines run per invocation (one, some, or all three depending on `target`), each with its own full 10-role agent roster and its own skill variant per role. The tracks share identical stage *structure* but differ in **what each stage is allowed to say**, enforced via a "Track Rules" block repeated verbatim at the bottom of every skill file in that track:

| Track | Agent/skill prefix | Code Inclusion | Tone | Mandatory diagrams |
|---|---|---|---|---|
| **End-User** | `user-*` / `user_*_agent` | **NONE** | Accessible, narrative, task-oriented | Mermaid **flowcharts** of user workflows/UI journeys |
| **Developer** | `dev-*` / `dev_*_agent` | **MINIMAL** — only truly essential snippets | Technical, architectural | Mermaid **architecture + sequence diagrams** |
| **AI Agent** | `agent-*` / `agent_*_agent` | **HIGH** — exact code refs, enumerations, paths, config keys required | Robotic, structured, YAML/JSON-like Markdown for machine parsing | *(none mandated)* |

Every track has the same 10 roles, each a separate agent + separate skill file:

| Role | Task (verbatim, condensed from the skill files — identical wording across all 3 tracks except the Track Rules block) |
|---|---|
| **Architect** | Traverse the target repo (`list_dir`, `view_file`) to determine scale. Output an exact number (N) of chunks and a scope per chunk. *"Do not hardcode 7."* |
| **Discovery** | Map the repository and output an inventory of high-level modules. |
| **Analysis** | Extract factual bullet points about functionality and behavior. |
| **Synthesis** | Generate a strict outline based on the analysis facts. |
| **Writer** | Assigned ONE chunk/chapter. Must use `grep_search`/`view_file` to inspect actual source before drafting — not just the provided summary. Write exhaustively about that one topic; do not summarize. |
| **Critic** | Review a drafted chunk against the codebase (`grep_search`, `view_file`). List required revisions, or output `APPROVED`. |
| **Compiler** | "Rolling Editor-in-Chief." Stitches N chunks sequentially: seed master with chunk 1; for each next chunk, take the last 2000 chars of master + first 2000 chars of the new chunk, smooth that seam, then splice via Python: `(master minus last 2000) + (smoothed seam) + (new chunk minus first 2000)`. Repeat for all chunks. |
| **Review** | Review the compiled master document for consistency and cross-chapter contradictions. |
| **Grounding** | Final pass: check every concrete claim against the target codebase. |
| **Exporter** | Run `npx --yes md-to-pdf <input.md>` on the finalized Markdown to produce a styled PDF. |

Each of the 30 track-specific agents (10 roles × 3 tracks) follows one exact template — a `hidden: true` agent whose entire job is to point at its skill file:

```yaml
---
name: user_discovery_agent
description: Discovery Agent for End-Users.
tools: [send_message, grep_search, view_file, list_dir, read_url_content, search_web, write_to_file, run_command]
hidden: true
---
# Agent System Instructions
You are the Discovery Agent for End-Users.
Before taking any action, you MUST read your strict skill instructions at
`C:\Users\Devang\.gemini\config\plugins\absorb\skills\user-discovery\SKILL.md`.
```

(swap `user`→`dev`/`agent` and `Discovery`→ any of the 10 roles above for the other 29). Every agent in the doc-gen pipeline shares the identical 8-tool toolset; none of them override `model` or carry an inline `system_prompt` — all real behavior comes from the skill file they're pointed at.

## 5. The Commit Analyzer sub-system

A separate, smaller pipeline, triggered via the `analyze_commit_delta` MCP tool (§2) or the described `/`-style invocation of the `commit-analyzer` skill directly. Three roles, not ten — no Architect/Critic/Review/Grounding/Exporter stages, no per-audience tracks.

| Role | Agent path | Skill path | Notes |
|---|---|---|---|
| Orchestrator | `agents/commit_analyzer_agent/agent.md` | `skills/commit-analyzer/SKILL.md` | `model: pro`, `enable_write_tools: true`, `enable_subagent_tools: true`, full inline `system_prompt` (not a "read the skill" pointer — the only agent in this repo with meaningful content directly in `agent.md`). |
| Writer (×N) | `agents/commit_writer_agent/agent.md` | `skills/commit-writer/SKILL.md` | `model: pro`, `enable_write_tools: true`. One instance spawned per commit chunk. |
| Compiler | `agents/commit_compiler_agent/agent.md` | `skills/commit-compiler/SKILL.md` | `model: pro`, `enable_write_tools: true`. |

**Flow, as literally specified in `commit-analyzer`'s skill:**
1. Orchestrator runs `git log --oneline {commit_start}..{commit_end}` to count commits.
2. Divides commits into chunks of ~4–5 commits each (e.g. 28 commits → 6–7 chunks), computing exact `start_hash`/`end_hash` per chunk.
3. Spawns one `commit_writer_agent` per chunk **simultaneously** via `invoke_subagent`, each writing to `scratch/chunk_{index}.md` (path relative to the target repo, not this plugin).
4. Each Writer runs `git show {commit_hash}` on **every single commit** in its chunk, and documents, per commit: **WHAT** changed, **WHY** (technical intent), a **code snippet** (diff-formatted, relevant lines only), and a **Risk Assessment** using one of three literal GitHub alert markers:
   - `> [!WARNING] Breaking Change:` — breaks existing contracts/schemas
   - `> [!CAUTION] High Risk:` — modifies critical core logic or security
   - `> [!NOTE] Low Risk:` — UI tweaks, docs, safe additions
5. Once all Writers report done, Orchestrator spawns one `commit_compiler_agent`, which reads every `scratch/chunk_*.md`, writes an Executive Summary + Component Breakdown, then stitches: Executive Summary → Component Breakdown → all chunks in chronological order.
6. Final report: `d:\working docs\Delta_Commit_Docs\Commit_Delta_Report_{commit_start}_to_{commit_end}.md`.

## 6. Known issues found while writing this document

Reported rather than silently fixed — see recommendation for each:

1. **Malformed output path in the main orchestrator skill.** `skills/absorb/SKILL.md`, final line, literally reads `d:\working docsbsorb_docs\<target>\` — missing a path separator, almost certainly meant to read `d:\working docs\absorb_docs\<target>\` (matching `server.py`'s `DOCS_DIR`). As written, an agent following this instruction literally would likely create a folder literally named `docsbsorb_docs` next to `working docs`, not inside it — meaning the MCP resource `absorb://docs/{target}/{module}` (which reads from the correctly-formed `d:\working docs\absorb_docs\...`) would never find what the pipeline just wrote. **Recommendation:** fix the path string in the skill file to match `server.py`'s `DOCS_DIR` exactly.
2. **`absorb_*` legacy agent/skill family appears to be dead code** (§4) — six agents and six skills with no live caller in the current orchestrator. **Recommendation:** either delete them, or add a comment at the top of each marking them explicitly superseded, so a future maintainer doesn't assume they're a valid alternate entry point.
3. **No per-track completeness enforcement.** Every Writer skill says "write exhaustively," but nothing in the Architect/Synthesis stage produces a checklist the Critic can verify against — the Critic's own skill just says "identify missing critical facts," with no defined source for what "complete" means. In practice (see the companion review in this repo's history) this allowed a full pipeline run to produce a materially thin user-facing document without any stage flagging it. **Recommendation:** have Synthesis emit an explicit per-chunk fact/coverage checklist, and have Critic check against that checklist specifically, not just its own judgment.
4. **Self-grounding, not adversarial grounding.** The Grounding stage is one agent checking its own track's compiled document — there's no separate agent whose only job is to try to disprove claims in the draft. **Recommendation:** see the plugin's SKILL.md changes made alongside this document (or planned, if not yet applied) for a stronger grounding pass.
5. **`docs/` folder does not previously exist in this plugin repo** — this file and any future documentation should live under `docs/` to keep it separate from the `agents/`/`skills/` runtime tree.
